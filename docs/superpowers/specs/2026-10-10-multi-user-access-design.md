# Многопользовательский доступ Walt P2P Monitor

Дата: 2026-10-10  
Статус: на согласовании

## 1. Цель

Преобразовать действующий однопользовательский Walt P2P Monitor в закрытый многопользовательский бот. Доступ выдаёт только администратор с Telegram ID `768929900`. Каждый допущенный пользователь работает со своим Walt P2P API-токеном и имеет полностью изолированные правила, расписания, уведомления и состояние интерфейса.

Изменение не добавляет автоматическую торговлю, операции с кошельком, платёжную систему или новые источники котировок.

## 2. Роли и состояния доступа

Роли:

- `ADMIN` — администратор `768929900`; рассматривает заявки и управляет пользователями.
- `USER` — обычный пользователь со всеми существующими функциями мониторинга.
- `PREMIUM` — зарезервированная роль для будущего платного доступа. В этой версии набор функций совпадает с `USER`.

Состояния доступа:

- `PENDING` — контакт подтверждён, заявка ожидает решения администратора.
- `AWAITING_TOKEN` — заявка одобрена, ожидается Walt API-токен.
- `ACTIVE` — токен проверен, доступ разрешён.
- `REJECTED` — заявка отклонена.
- `REVOKED` — ранее выданный доступ отозван.

Администратор всегда имеет роль `ADMIN` и состояние `ACTIVE`. Бот не позволяет отозвать доступ, изменить роль или удалить администратора через интерфейс.

## 3. Регистрация пользователя

1. Неизвестный пользователь отправляет `/start`.
2. Бот показывает русское объяснение и системную кнопку Telegram «Отправить номер телефона».
3. Принимается только объект `Contact`, у которого `contact.user_id` совпадает с ID отправителя. Номер, введённый обычным текстом, не принимается.
4. Телефон нормализуется, проверяется на допустимый формат и должен быть уникальным среди неудалённых пользователей.
5. Создаётся или обновляется заявка со статусом `PENDING`.
6. Администратору приходит сообщение с именем, username, Telegram ID и телефоном, а также кнопками «Разрешить» и «Отклонить».
7. Повторный `/start` не создаёт дубликат заявки, а показывает текущее состояние.

Телефон используется только для идентификации заявки и администрирования доступа. Он не записывается в журналы и не передаётся внешним сервисам.

## 4. Одобрение и Walt API-токен

После нажатия администратором «Разрешить»:

1. Статус пользователя атомарно меняется с `PENDING` на `AWAITING_TOKEN`.
2. Пользователю отправляется запрос личного Walt P2P API-токена.
3. Следующее текстовое сообщение принимается как токен только в соответствующем FSM-состоянии и сразу удаляется из чата существующим middleware.
4. Токен проверяется безопасным запросом списка онлайн-объявлений Walt. Он не включается в текст ошибок и журналы.
5. При HTTP 401/403 токен считается недействительным, не сохраняется, пользователь остаётся в `AWAITING_TOKEN` и может повторить ввод.
6. При сетевой ошибке, 429 или 503 доступ не активируется; пользователь получает предложение повторить позже.
7. После успешной проверки токен шифруется, сохраняется и только затем состояние меняется на `ACTIVE`.

Команда `/token` и кнопка «Токен Walt» позволяют активному пользователю безопасно заменить токен. Текущее значение никогда не показывается. Ошибка проверки нового токена не уничтожает ранее работавший токен.

## 5. Хранение секретов

Для шифрования используется `cryptography.fernet`. Ключ `CREDENTIAL_ENCRYPTION_KEY` хранится только в `/etc/walt-price-bot.env` и не попадает в SQLite, Telegram, журнал или Git.

Серверный установщик при отсутствии ключа генерирует 32 случайных байта через системный генератор, кодирует их в URL-safe Base64 и дописывает переменную в защищённый env-файл с правами `0600`. Существующий ключ при повторной установке не меняется.

Сервис завершается с явной ошибкой до запуска polling, если ключ отсутствует или повреждён. Потеря ключа не должна приводить к молчаливому удалению токенов.

Текущий `WALT_API_KEY` сохраняется для обратной совместимости. При первом запуске новой версии, если у администратора ещё нет зашифрованного токена, значение `WALT_API_KEY` проверяется, шифруется и привязывается к администратору. После миграции переменная остаётся допустимой, чтобы обновление не требовало немедленных действий владельца.

## 6. Изоляция данных

Все пользовательские данные связываются с `telegram_id`:

- пауза уведомлений и ID последнего сообщения;
- ценовые и процентные правила;
- расписания и время последней отправки;
- настройки выгодных лотов;
- история отправленных объявлений;
- зашифрованный Walt-токен.

Методы репозитория для пользовательских данных обязательно принимают `telegram_id`. Обработчики получают ID только из проверенного Telegram-события. Администратор не может случайно открыть или изменить чужие торговые настройки через обычное меню.

Фоновый монитор получает список `ACTIVE` пользователей, расшифровывает токен непосредственно перед созданием Walt-клиента и обрабатывает каждого пользователя независимо. Ошибка токена, Walt, Coinbase, SQLite или Telegram одного пользователя не останавливает остальных. Одновременные запросы ограничиваются локальным семафором, чтобы число пользователей не создавало всплеск запросов Walt.

Coinbase остаётся общим справочным источником; его актуальные курсы могут использоваться всеми пользователями в рамках одного цикла. Walt всегда вызывается с токеном конкретного пользователя.

## 7. Админ-панель

Администратору доступны команда `/admin` и кнопка «Админ-панель» в его главном меню. Другим пользователям они не показываются, а прямые команды и callback-запросы отклоняются серверной проверкой роли.

Панель содержит:

- ожидающие заявки;
- активных пользователей;
- отклонённых и отозванных пользователей;
- карточку пользователя: Telegram ID, имя, username, телефон, роль, статус, даты заявки и активации, наличие токена без показа значения;
- действия «Разрешить», «Отклонить», «Отозвать доступ», «Вернуть доступ», «Сделать USER», «Сделать PREMIUM», «Удалить»;
- постраничный список по 10 записей;
- кнопку возврата в главное меню.

Операции повторяемы и безопасны для устаревших кнопок. Удаление требует отдельного подтверждения. Оно удаляет пользователя, телефон, токен, правила, расписания, настройки и историю в одной транзакции. Отзыв доступа только переводит пользователя в `REVOKED`: данные и токен сохраняются для возможного восстановления.

## 8. Telegram-интерфейс

Существующие команды сохраняются:

`/start`, `/price`, `/deals`, `/alert`, `/change`, `/schedule`, `/alerts`, `/delete`, `/pause`, `/resume`, `/help`.

Добавляются:

- `/token` — ввод или безопасная замена Walt API-токена;
- `/admin` — панель администратора.

Русские тексты, модель одного актуального сообщения и удаление пользовательских сообщений сохраняются. Состояние последнего сообщения хранится отдельно для каждого пользователя. Служебные уведомления о заявках отображаются администратору через ту же защищённую модель замены сообщения; все ожидающие заявки всегда доступны из панели.

## 9. SQLite и миграция

Добавляются таблицы:

- `users` — профиль, телефон, роль, статус и временные метки;
- `user_credentials` — один зашифрованный Walt-токен на пользователя;
- `user_settings` — пауза и последнее Telegram-сообщение.

Существующие таблицы `alerts`, `schedules`, `opportunity_settings` и `opportunity_notification_history` получают принадлежность пользователю через безопасное пересоздание и копирование внутри транзакции.

Миграция:

1. Создаёт администратора `768929900`.
2. Переносит существующие правила, расписания, настройки, паузу, последнее сообщение и историю к администратору.
3. Не удаляет старые данные до успешного копирования.
4. Проверяет количество перенесённых записей до фиксации транзакции.
5. Является идемпотентной и допускает повторный запуск.
6. Использует существующую серверную резервную копию перед обновлением.

Внешние ключи используют `ON DELETE CASCADE`, чтобы подтверждённое удаление пользователя не оставляло секреты или разрозненные данные.

## 10. Авторизация

Каждый защищённый message- и callback-обработчик выполняет серверную проверку пользователя:

- `ACTIVE` или `ADMIN` — доступ к обычным функциям;
- `PENDING` — сообщение «Заявка ожидает решения»;
- `AWAITING_TOKEN` — переход к вводу токена;
- `REJECTED` — сообщение об отклонении и возможность отправить новую заявку через контакт;
- `REVOKED` — сообщение об отзыве доступа;
- неизвестный пользователь — регистрационный сценарий.

Проверка интерфейсной кнопкой не считается авторизацией. Все callback ID валидируются, а административные операции дополнительно проверяют неизменяемый ID администратора.

## 11. Обработка ошибок

- Неуспешная отправка Telegram не отмечает заявку, уведомление или расписание доставленным.
- Неуспешная проверка нового токена не заменяет старый токен.
- Ошибка расшифрования блокирует только соответствующего пользователя и записывает обезличенное сообщение без токена.
- Повторное одобрение, отклонение или отзыв возвращает актуальное состояние без исключения.
- Удалённые и устаревшие callback-кнопки не создают необработанных ошибок.
- Все изменения роли, статуса и секретов выполняются транзакционно.

## 12. Тестирование

Обязательные проверки:

1. Администратор `768929900` создаётся и не может быть удалён или понижен.
2. Чужой или текстовый номер телефона не принимается.
3. Нативный контакт создаёт ровно одну заявку.
4. Администратор получает заявку и только он может её обработать.
5. Отклонение и повторная заявка работают предсказуемо.
6. Одобрение переводит пользователя в ожидание токена.
7. Неверный токен не сохраняется, успешный шифруется и активирует доступ.
8. Токен отсутствует в SQLite в открытом виде, `repr`, журнале и Telegram-ответах.
9. Замена токена атомарна и сохраняет старый при ошибке.
10. USER и PREMIUM имеют доступ, но не могут открыть `/admin`.
11. Изменение роли сохраняется после перезапуска.
12. Отзыв немедленно прекращает мониторинг пользователя.
13. Возврат доступа сохраняет настройки и токен.
14. Удаление каскадно удаляет PII, токен и пользовательские данные.
15. Два пользователя не видят и не запускают правила друг друга.
16. Фоновый цикл использует разные Walt-токены для разных пользователей.
17. Сбой одного пользователя не блокирует другого.
18. Миграция версии 1.4.0 переносит все данные администратору без потерь.
19. Миграция повторяема.
20. Все прежние команды и текущие 121 тест продолжают работать после адаптации.

## 13. Развёртывание

Перед обновлением установщик останавливает службу и создаёт резервную копию SQLite. Затем он сохраняет существующий env-файл, генерирует `CREDENTIAL_ENCRYPTION_KEY` только при отсутствии, устанавливает зависимости, запускает миграцию и стартует systemd-службу.

Проверка выпуска включает:

- полные pytest, Ruff и compileall;
- проверку миграции на копии старой базы;
- отсутствие секретов в Git;
- активную systemd-службу;
- наличие администратора, новой схемы и зашифрованной учётной записи;
- отсутствие токенов и телефонов в журнале.

## 14. Критерии готовности

Функция готова, когда неизвестный пользователь не может использовать мониторинг, подтверждённый контакт создаёт заявку, администратор управляет доступом и ролями, пользователь активируется только после проверки собственного зашифрованного Walt-токена, данные разных пользователей изолированы, прежняя база мигрирует без потерь, а сервер продолжает работать после обновления.
